1. EXECUTIVE SUMMARY & ARCHITECTURAL OVERVIEW
--------------------------------------------------------------------------------
Following the stabilization baseline established in Checkpoint v2, engineering efforts
focused on eliminating hard concurrency deadlocks within the native audio engine,
resolving asynchronous race conditions in the stream pacing subsystem, and strictly
aligning the desktop client and relay server with Ollalink's real-time Sound-Stream
wire specifications.

The desktop translation architecture operates across three synchronized execution tiers:
  1. Real-Time Native Audio Core (Rust / CPAL / Tokio):
     Manages hardware microphone capture, real-time Voice Activity Detection (VAD) with
     dynamic echo suppression scaling, Catmull-Rom cubic spline resampling (16kHz/24kHz/
     44.1kHz/48kHz), jitter buffer management, and outbound frame pacing.
  2. Desktop Client UI Bridge (TypeScript / Rust IPC):
     Processes UI interaction, manages bidirectional audio and text channels with the
     local relay, orchestrates audio playback buffer lifecycles, and formats live captions.
  3. Local High-Throughput Relay (Node.js):
     Multiplexes multi-party desktop room audio, manages authenticated upstream
     WebSocket sessions to Ollalink Sound-Stream, orchestrates upstream reconnect backoff,
     enforces frame send pacing (50 fps @ 20ms), and inspects configuration capabilities.

Throughout this period, 15 critical, high, and medium defects were diagnosed, patched,
and comprehensively verified with 135 automated server test suites and 12 native Rust
test suites (including 10,000-cycle concurrent thread contention tests).

[BUG 24] CRITICAL DEADLOCK: LOCK-ORDER INVERSION IN JITTERPLAYER
--------------------------------------------------------------------------------
- Severity: CRITICAL (Complete freeze of audio output and capture thread contention)
- Affected Files: app/src-tauri/src/audio/jitter.rs (lines 188-193 vs 277-278)
- Architecture & Concurrency Context:
  Audio output in the native desktop client is driven by a high-priority, real-time
  CPAL hardware callback thread running `fill_into()`. Concurrently, the asynchronous
  Tokio sender task running `run_sender_watch()` in `audio/mod.rs` periodically queries
  `is_playing()` to determine whether the desktop speakers are actively rendering sound,
  in order to dynamically scale the VAD threshold by 3x and suppress acoustic feedback.

- Root Cause Analysis:
  A classic circular lock-order inversion existed between `JitterPlayer.ring` (a
  `parking_lot::Mutex<VecDeque<f32>>`) and `JitterPlayer.playing` (a `parking_lot::Mutex<bool>`):
    * Thread A (CPAL Audio Callback Thread - `fill_into`):
        Step 1: Acquired `self.ring.lock()` to pull PCM audio samples.
        Step 2: Acquired `self.playing.lock()` to update the playback state flag.
        Step 3: Acquired `self.consecutive_empty.lock()` to track buffer underflow.
    * Thread B (Tokio Async Sender Thread - `is_playing`):
        Step 1: Acquired `self.playing.lock()` to check if playback was flagged active.
        Step 2: Acquired `self.ring.lock()` to verify if samples remained in the buffer.
  Under heavy CPU load or during simultaneous speech transmission and peer playback,
  Thread A held `ring` and waited on `playing`, while Thread B held `playing` and waited
  on `ring`. Because `parking_lot::Mutex` uses adaptive spin-waiting followed by thread
  parking, the real-time audio callback thread permanently froze, causing silent audio,
  missed buffer deadlines, and eventual OS audio device invalidation.

- Concrete Engineering Solution:
  1. Converted `playing` from `Mutex<bool>` to `std::sync::atomic::AtomicBool`.
  2. Converted `consecutive_empty` from `Mutex<usize>` to `std::sync::atomic::AtomicUsize`.
  3. Redesigned `is_playing(&self) -> bool` to be lock-free on the initial check:
     ```rust
     pub fn is_playing(&self) -> bool {
         if !self.playing.load(Ordering::Acquire) {
             return false;
         }
         !self.ring.lock().is_empty()
     }
     ```
  4. Redesigned `fill_into(&self, output: &mut [f32])`:
     The function now locks ONLY `self.ring`. Buffer underflow counts and playback state
     transitions are written using atomic operations (`store(false, Ordering::Release)`).
     Nested locking is completely eliminated.
  5. Stress Test Verification:
     Implemented `test_jitter_player_concurrent_fill_and_is_playing_no_deadlock`.
     Spawns two competing threads executing 10,000 continuous iterations of interleaved
     `fill_into` and `is_playing` across active and empty buffer states. Verified 0 deadlocks.

[BUG 25] CAPTIONS STATE SYNCHRONIZATION PROTOCOL MISMATCH
--------------------------------------------------------------------------------
- Severity: MEDIUM (Functional failure of caption toggle control in desktop UI)
- Affected Files: app/ui/src/bridge.ts, bridge.js (line 732) vs server/src/server.js (line 460)
- Root Cause Analysis:
  The desktop client UI bridge emitted `{ type: 'captions-toggle' }` over the local
  WebSocket control channel when the user toggled the captions switch. However, the relay
  server message dispatcher strictly checked `case 'captions.set': client.captionsEnabled = !!msg.on;`.
  Because the type did not match, the event fell through as an unhandled message,
  leaving captions stuck in their default state.
- Concrete Engineering Solution:
  1. Updated `bridge.ts` and compiled `bridge.js` to dispatch the canonical schema:
     `ws.send(JSON.stringify({ type: 'captions.set', on: nextState }));`.
  2. Hardened `server.js` to support both forms:
     ```javascript
     case 'captions.set':
     case 'captions-toggle':
       client.captionsEnabled = msg.type === 'captions-toggle' ? !client.captionsEnabled : !!msg.on;
       broadcastRoomMeta(client.room);
       break;
     ```

[BUG 26] STALE AUDIO BUFFER FLUSH ON ABNORMAL-CLOSE RECONNECT
--------------------------------------------------------------------------------
- Severity: MEDIUM (Up to 16 seconds of stale audio dumping into new sessions)
- Affected Files: server/src/server.js (lines 765-767)
- Root Cause Analysis:
  While the explicit overload handler (`handleUpstreamOverloaded`) trimmed
  `client.upstreamQueue` to the most recent 2 frames (`.slice(-2)`), the abnormal-close
  reconnect path (`handleUpstreamClose` -> `scheduleUpstreamReconnect`) failed to trim
  the queue. If an upstream socket closed abnormally (TCP RST, TLS drop, or network
  jitter), up to 100 frames (~16 seconds of unpaged audio) accumulated in the queue.
  When the new session reached `session.ready`, this massive backlog dumped into Ollalink
  in a rapid burst, causing immediate translation latency and re-triggering overload drops.
- Concrete Engineering Solution:
  Added universal audio queue trimming directly inside `scheduleUpstreamReconnect`:
  ```javascript
  function scheduleUpstreamReconnect(client, reason = 'unknown') {
    // ...
    // Trim queue on all reconnect triggers to prevent stale audio burst into new session
    if (client.upstreamQueue && client.upstreamQueue.length > 2) {
      client.upstreamQueue = client.upstreamQueue.slice(-2);
    }
    // ...
  }
  ```

[BUG 27] RECONNECT COUNTER DOUBLE-INCREMENTING ON OVERLOADED SOCKET CLOSE
--------------------------------------------------------------------------------
- Severity: MEDIUM (Shortened effective reconnect budget from 5 attempts to 2-3)
- Affected Files: server/src/server.js (lines 691, 761)
- Root Cause Analysis:
  When Ollalink closed due to an overloaded condition, it sent an error event followed
  immediately by a WebSocket `close` event.
    1. `handleUpstreamOverloaded` received the error and called `scheduleUpstreamReconnect(client)`,
       incrementing `client.reconnectAttempts` (e.g. from 0 to 1).
    2. The socket close event arrived ~20ms later. `handleUpstreamClose` observed that
       `_lastOverloaded` was < 2000ms and called `scheduleUpstreamReconnect(client)` a
       second time, incrementing `client.reconnectAttempts` from 1 to 2.
  As a result, each overload incident consumed two retry attempts. After only 3 overloads,
  the relay exceeded the 5-attempt ceiling and permanently severed the call.
- Concrete Engineering Solution:
  In `handleUpstreamClose`, added a state check to prevent double-scheduling:
  ```javascript
  if (isOverloadClose) {
    if (client.reconnectTimer) {
      // Reconnect is already scheduled by handleUpstreamOverloaded; do not double-increment
      return;
    }
  }
  ```

[BUG 28] DOUBLE PACING LOOP: TIMEOUT LEAK ACROSS RECONNECTS
--------------------------------------------------------------------------------
- Severity: MEDIUM (Runaway send rate causing recursive overload loops)
- Affected Files: server/src/server.js (lines 1005-1008)
- Root Cause Analysis:
  `schedulePacedUpstreamSend` invoked `setTimeout` recursively to pace outbound audio
  at ~20ms per frame. However, the timer handle was not retained on the `client` struct.
  When a reconnect occurred, the active `setTimeout` continued to fire in the background
  while the new session's `onReady` initiated a second pacing loop. With two concurrent
  loops draining frames, the transmission rate doubled to 2.0x real-time, instantly
  violating Ollalink's rate limit and triggering immediate `overloaded` socket closures.
- Concrete Engineering Solution:
  1. Stored the timer handle on `client.upstreamPacingTimer`.
  2. Cleared the active timer before initiating reconnects, during `bindUpstream`,
     and on client disconnection:
     ```javascript
     if (client.upstreamPacingTimer) {
       clearTimeout(client.upstreamPacingTimer);
       client.upstreamPacingTimer = null;
     }
     ```

[BUG 29] TTS LANES COLLAPSING TO SINGLE KEY FOR STRING ARRAYS
--------------------------------------------------------------------------------
- Severity: MEDIUM (Audio decoded at wrong sample rate for non-default target languages)
- Affected Files: server/src/server.js (lines 786-795)
- Root Cause Analysis:
  When Ollalink upstream returned `config_applied.tts.lanes` as a sequential array of
  lane modes (e.g. `['stream', 'stream']`) rather than an object map,
  `inspectSessionReadyConfig` iterated over the entries and wrote each one to:
  `client.targetLanes[defaultLang] = lane;`.
  Every iteration overwrote the entry for `defaultLang`, discarding lane metadata for all
  other languages in multi-party desktop calls.
- Concrete Engineering Solution:
  Updated array parsing to map elements by index to the session's target language array:
  ```javascript
  if (Array.isArray(rawLanes)) {
    const targetLangs = client.session?.targetLang ? [client.session.targetLang] : [];
    rawLanes.forEach((lane, idx) => {
      const langKey = targetLangs[idx] || defaultLang;
      client.targetLanes[langKey] = lane;
    });
  }
  ```

[BUG 30] TARGET LANES KEY MISMATCH WITH REGION LOCALE TAGS
--------------------------------------------------------------------------------
- Severity: MEDIUM (Cache miss leading to incorrect audio playback sample rate)
- Affected Files: server/src/server.js (lines 790, 1037)
- Root Cause Analysis:
  Lane keys stored in `client.targetLanes` were indexed by base language codes (e.g. `'hi'`),
  but audio translation payloads from Ollalink arrived with full regional tags
  (e.g. `p.language = 'hi-IN'`).
  Looking up `client.targetLanes['hi-in']` resulted in a cache miss, causing the relay to
  fall back to assuming 24kHz stream mode for what was actually a 48kHz batch WAV lane.
- Concrete Engineering Solution:
  1. Normalized lane cache keys by stripping region subtags:
     `const normLang = lang.toLowerCase().split(/[-_]/)[0];`
  2. In `forwardOllalinkToRoom`, implemented fallback key resolution:
     `const laneMode = client.targetLanes[langBase] || client.targetLanes[p.language] || 'stream';`

[BUG 31] PREMATURE STATE.CONFIGURED ASSERTION IN OLLALINK.JS
--------------------------------------------------------------------------------
- Severity: MEDIUM (Audio frames transmitted before upstream configuration validated)
- Affected Files: server/src/ollalink.js (line 214)
- Root Cause Analysis:
  `state.configured = true` was assigned inside the WebSocket send callback of
  `session.configure`, immediately after writing bytes to the TCP socket buffer.
  However, Ollalink has not validated or acknowledged configuration at that point;
  validity is only confirmed when Ollalink emits `session.ready`.
  Because `isConfigured()` returned true prematurely, `schedulePacedUpstreamSend` began
  streaming PCM frames before the upstream session initialized, risking `bad_configure`
  or socket reset.
- Concrete Engineering Solution:
  1. Removed `state.configured = true` and `handlers.onReady?.()` from the send callback.
  2. Enforced that `state.configured = true` and `onReady` trigger strictly when
     the upstream `session.ready` frame is received and parsed.
  3. Updated `server/test/receive_path.test.js` mock harness to acknowledge
     `session.configure` with `session.ready`.

[BUG 32] UTTERANCE DEDUPLICATION COLLISION ON UNDEFINED UTTERANCEID
--------------------------------------------------------------------------------
- Severity: MEDIUM (Initial audio chunk of utterances dropped, creating speech gaps)
- Affected Files: app/ui/src/bridge.ts, bridge.js (line 576)
- Root Cause Analysis:
  The audio deduplication cache generated keys as `${msg.sessionId}:${msg.utteranceId}:${msg.chunkSeq}`.
  When Ollalink emitted audio chunks without an explicit `utteranceId`, the key evaluated
  to `"sess-1:undefined:0"` for chunk 0 of every single sentence spoken.
  The first sentence played normally. For all subsequent sentences, chunk 0 was flagged
  as a duplicate and discarded, clipping off the first syllable or word of every sentence.
- Concrete Engineering Solution:
  Guarded the deduplication lookup with explicit validation:
  ```typescript
  if (msg.utteranceId && msg.utteranceId !== 'undefined' && msg.chunkSeq !== undefined) {
    const dedupKey = `${msg.sessionId || 'self'}:${msg.utteranceId}:${msg.chunkSeq}`;
    if (audioChunkDedupSet.has(dedupKey)) {
      return; // Skip genuine duplicate chunk
    }
    audioChunkDedupSet.add(dedupKey);
  }
  ```

--------------------------------------------------------------------------------
- Severity: MEDIUM (Triple UI voice update notifications and redundant room broadcasts)
- Affected Files: server/src/server.js (lines 910, 917, 1014), server/src/ollalink.js

    2. Inside `bindUpstream:onEvent` (`server.js:917`)

  2. Removed redundant invocations from `forwardOllalinkToRoom` and `onEvent`.
  3. Added a per-generation guard (`clientOwner._lastReadyGen`) ensuring idempotent
     execution exactly once per session configuration.

[BUG 34] GHOST WAV AUDIO DECODE ACROSS CALL BOUNDARIES
--------------------------------------------------------------------------------
- Severity: MEDIUM (Audio from previous call bleeding into new call)
- Affected Files: app/ui/src/bridge.ts, bridge.js (lines 199-297)
- Root Cause Analysis:
  When a user hung up or switched rooms, `stopAudio()` was invoked. However, an in-flight
  `await decodeAudioData()` operation on a large WAV chunk remained pending in the JS
  microtask queue. When the user initiated a new call, a new audio context was created.
  The stale promise then resolved, found an active context, and scheduled the previous
  call's audio at stale timestamp offsets.
- Concrete Engineering Solution:
  1. Introduced a monotonic generation counter: `let desktopPlaybackGen = 0;`.
  2. Incremented `desktopPlaybackGen++` inside `stopAudio()`.
  3. Captured `const currentGen = desktopPlaybackGen;` prior to `decodeAudioData()`.
  4. Verified `if (desktopPlaybackGen !== currentGen) return;` immediately after the
     promise resolved, safely discarding stale audio.
